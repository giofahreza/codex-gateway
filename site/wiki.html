Quick start

Applies to
Local and server installs
Time
5-10 minutes for first boot
Needed
Rust toolchain and config.json

Start IO Gateway locally, open the dashboard, then add provider accounts before routing production traffic.

  1. 1
    Build the binary.

    Run a release build so you test the same mode you deploy.

  2. 2
    Create the config file.

    Copy config.example.json to config.json and edit the listen address, shared proxy key, auth directory, and admin auth settings.

  3. 3
    Set the shared client key.

    Use IO_GATEWAY_KEY or proxy_api_key. Client requests send it as Authorization: Bearer ....

  4. 4
    Run IO Gateway.

    Start the binary and open http://127.0.0.1:8319/ for the dashboard.

  5. 5
    Add at least one provider account.

    The readiness endpoint only becomes useful after an enabled upstream account is available.

  6. 6
    Test a model from the dashboard.

    Use Settings -> Test API before changing Codex CLI, Claude Code, or application clients.

cargo build --release
cp config.example.json config.json
export IO_GATEWAY_KEY="your-shared-proxy-key"
./target/release/io-gateway
Default dashboard URL

Open http://127.0.0.1:8319/. Runtime Swagger UI is available at /docs/ when the gateway is running.

Configuration

File
config.json
Secrets
Proxy key, admin key, OAuth settings

IO Gateway reads core runtime settings from config.json and allows selected admin/OAuth values to be overridden by environment variables.

Minimum config

{
  "listen": "0.0.0.0:8319",
  "upstream_base": "https://chatgpt.com/backend-api/codex",
  "proxy_api_key": "your-shared-proxy-key",
  "tokens": [],
  "auth_dir": "./auths"
}

Important fields

  • listen Socket address for the dashboard and API server.
  • proxy_api_key Shared key for client API requests unless managed API keys are used.
  • auth_dir Directory where provider credential files are stored.
  • disabled_files Credential files that should load but start disabled.
  • admin_auth Dashboard key, TOTP secret, cookie security, and session lifetime.
  • trusted_proxy Enable only behind a reverse proxy that sanitizes forwarded IP headers.
  • history_retention_days How long usage history remains available for charts and summaries.

Admin auth environment overrides

ADMIN_AUTH_ENABLED=true
ADMIN_AUTH_API_KEY=your-admin-key
ADMIN_AUTH_TOTP_SECRET=BASE32_SECRET
ADMIN_AUTH_SESSION_TTL_SECONDS=43200
ADMIN_AUTH_SECURE_COOKIES=true
Use secure cookies behind HTTPS

Set ADMIN_AUTH_SECURE_COOKIES=true when the dashboard is served through HTTPS.

Dashboard

URL
/ on the gateway server
Auth
Admin API key and TOTP when enabled

The dashboard is the control plane for accounts, model tests, custom routes, API keys, notifications, and operational history.

Login

  1. 1
    Open the dashboard.

    Use the gateway root URL, for example http://127.0.0.1:8319/.

  2. 2
    Enter the admin key.

    This is admin_auth.api_key or the environment override.

  3. 3
    Enter the 6-digit TOTP code.

    Use the authenticator app configured from admin_auth.totp_secret.

Main dashboard areas

Overview

Total requests, error rate, account count, and attention states.

Providers

Account cards with health, quota, usage, enable/disable, delete, refresh, and re-auth controls.

Custom Models

Create and manage ctm: aliases with fallback and load balancing.

Settings

Test API, managed API keys, notification channels, and alert subscriptions.

    Open the provider section.

Custom models

Prefix
ctm:
Use when
You want stable aliases with fallback

Custom models are first-class gateway routes. They let operators expose stable names while changing provider targets, account rules, and fallback behavior behind the scenes.

Create a custom model

  1. 1
    Open Custom Models in the dashboard.

    This section manages aliases that clients call as ctm:name.

  2. 2
    Choose an alias name.

    Use a stable operational name such as ctm:workhorse, ctm:research, or ctm:fast.

  3. 3
    Add provider targets.

    Each target points to a provider model and can optionally select a specific account.

  4. 4
    Set weights and fallback order.

    Use weighting for load distribution and fallback order for controlled failover.

  5. 5
    Save the alias.

    The alias appears in the model catalog and can be called by clients.

  6. 6
    Run a Test API prompt.

    Verify the route before giving it to clients or scoped API keys.

Supported custom-model behavior

  • Multiple provider targets Route one alias to several providers or models.
  • Specific account targeting Pin a target to one upstream account when needed.
  • Account exclusion Use every account except a selected account for maintenance or isolation.
  • Weighted load balancing Give preferred targets more traffic while keeping backups available.
  • Fallback chains Try another target when a provider fails, cools down, or runs out of quota.
{
  "model": "ctm:research",
  "targets": [
    { "model": "cld:claude-sonnet-4", "weight": 3 },
    { "model": "gem:gemini-3-pro", "weight": 1 },
    { "model": "glm:glm-4.5", "weight": 1 }
  ]
}

Test API

Location
Settings -> Test API
Key needed
No client API key

Test API lets an operator ask quick questions or validate model routes directly inside the dashboard without creating a separate client API key.

  1. 1
    Open Settings.

    Use the dashboard settings modal after admin login.

  2. 2
    Open Test API.

    The test panel uses the gateway's own dashboard session.

  3. 3
    Select a model.

    Choose a provider-prefixed model such as glm:glm-4.5 or a custom alias such as ctm:research.

  4. 4
    Send a small prompt.

    Use a short question to verify account auth, model availability, and response conversion.

  5. 5
    Inspect the result.

    If it fails, check provider account health, API key access rules, custom model targets, and quota state.

Best use

Use Test API before changing client configs, before publishing a new custom model alias, and after re-authing an account.

API keys

Location
Dashboard Settings
Scopes
Provider and account rules

Managed API keys let you give clients gateway access without sharing the admin dashboard key or upstream provider credentials.

Create a key

  1. 1
    Open Settings -> API Keys.

    Only dashboard admins can create or revoke managed keys.

  2. 2
    Create a new key.

    Give it a readable label so you know which app or user owns it.

  3. 3
    Choose access.

    Leave unrestricted, limit to providers, or limit to selected accounts inside providers.

  4. 4
    Copy the key once.

    Store it in the client environment or secret manager.

Common access patterns

All providers

Use for trusted internal tools that should follow gateway routing.

One provider

Use when a client should only access Claude, Gemini, GLM, or another single provider.

Selected accounts

Use when you need cost, team, or tenant separation.

Custom aliases

Access rules are enforced before dispatch, including requests routed through ctm: aliases.

Notifications

Channels
Telegram, Google Chat
Use for
Auth, error, and quota alerts

Notifications warn you when an account or model needs attention before client requests begin failing.

  1. 1
    Open Settings -> Notifications.

    Choose Telegram or Google Chat webhook delivery.

  2. 2
    Enter channel credentials.

    For Telegram, configure the bot token and chat target. For Google Chat, configure the webhook URL.

  3. 3
    Send a test notification.

    Verify delivery before relying on alerts.

  4. 4
    Subscribe accounts or quotas.

    Choose which account or model quota events should send messages.

Typical alerts

  • Authentication error Account needs re-authentication or credential refresh.
  • Upstream error Provider returned an error that needs attention.
  • Quota exhausted Model or account quota is fully used.
  • Quota available again A previously blocked model/account can accept traffic again.

Tracks
Requests, errors, tokens, quota state

IO Gateway records operational history so you can see which accounts are used, which models are failing, and which upstreams are running out of quota.

Dashboard views

Context Usage

Charts input, output, cache, reasoning, and total tokens over time.

Provider quota

Shows provider-specific windows, balance, reset time, package data, and model breakdown when available.

Account health

Tracks last seen, last success, latest error, request counts, and active streams.

History filters

Use time range, bucket size, model breakdown, and account filters to narrow operational data.

Deployment

Recommended
GitHub Actions release workflow
Health
/health and /ready

The production workflow should build in CI, upload the exact binary artifact, restart the systemd service, and verify health before declaring deployment complete.

Release deployment flow

  1. 1
    Push a release tag or run the workflow manually.

    The deploy workflow is intended for v* tags and manual dispatch.

  2. 2
    Run checks in GitHub Actions.

    CI should run formatting, dashboard JavaScript syntax checks, tests, and release build.

  3. 3
    Upload the built artifact.

    The server should receive the GitHub-built binary, not build from a dirty local checkout.

  4. 4
    Install and restart.

    Back up the live binary, install the new one, and restart io-gateway.service.

  5. 5
    Verify readiness.

    Check /health, /ready, service state, and revision metadata.

curl http://127.0.0.1:8319/health
curl http://127.0.0.1:8319/ready

Troubleshooting

Start with
Dashboard health and logs
Then check
Provider auth, quota, access rules

Most gateway problems are caused by missing enabled accounts, expired provider auth, scoped API keys blocking access, or custom model aliases without eligible targets.

ProblemCheckFix
/ready failsNo enabled healthy upstream account.Add or enable an account, refresh quota, or re-auth a provider.
401 from clientWrong shared key or revoked managed API key.Use the correct bearer token or create a new managed key.
Custom model failsNo eligible target for the ctm: alias.Check target provider, account access, account health, and fallback order.
Provider returns auth errorsExpired OAuth token, invalid API key, or changed upstream session.Run provider re-auth or replace the API key.
Model disappears from catalogProvider disabled, account unavailable, or custom model deleted.Refresh dashboard data and verify provider/account status.
Notifications do not sendInvalid Telegram or Google Chat settings.Use the notification test button and verify bot/webhook credentials.

Fast diagnostic checklist

  1. 1
    Open the dashboard.

    Look for attention cards, latest errors, disabled accounts, and quota states.

  2. 2
    Run Test API.

    Test the exact model or custom alias that failed from a client.

  3. 3
    Check access rules.

    Confirm the client API key can use the requested provider/account/custom alias path.

  4. 4
    Read service logs.

    Use systemd or process logs to inspect upstream response details and gateway errors.
