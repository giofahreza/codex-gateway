Account operations

Account policy before every request.

These controls matter when several upstream accounts share one client-facing gateway and traffic needs predictable dispatch rules.

Priority drain to quota Mark one or more accounts as Use first. IO Gateway sends traffic there until the account is disabled, cooling down, unavailable, or fully used.
Prompt limits at three scopes Set estimated prompt-token ceilings for a client key globally, per provider, or per upstream account before a request is dispatched.
Provider-aware account setup Add Codex, Claude, Gemini, Qwen, Grok, Copilot, GLM, and direct API-key accounts through provider-specific flows.
Route aliases Create ctm: models with provider targets, weights, fallback steps, account targeting, and dashboard test checks.
Operator signals Use quota snapshots, cooldown state, recent errors, usage history, and notifications as routing and maintenance inputs.
Routing policypriority, fallback, cooldowns
  • Use-first accounts Drain selected accounts before the normal pool.
  • Disabled account guard Priority is ignored automatically when an account is disabled.
  • Quota-aware fallback Skip unavailable, cooling-down, or exhausted routes.
  • Weighted custom targets Spread aliases across providers and accounts.
Access controlclient keys and prompt ceilings
  • Whole-key limit Cap estimated prompt tokens for everything a key can send.
  • Provider limit Apply different ceilings to Codex, Claude, Gemini, and other providers.
  • Account limit Protect individual upstream accounts from oversized prompts.
  • Scoped routes Restrict keys to specific providers, accounts, or model aliases.

Users call the gateway. Operators keep provider credentials private and manage accounts, keys, custom models, usage, and notifications from a local UI.

  • Add accounts OAuth, device login, browser-token fallback, and API-key entry stay inside the operator surface.
  • Test before routing The toolbar Test API action sits next to Add account and sends prompts through provider routes or ctm: aliases.
  • Bound client access API keys can be scoped by provider, account, and prompt size.
Product controls

Every routing claim has an operator view.

The dashboard exposes account priority, quota state, key limits, custom routes, and route testing as concrete controls instead of hidden config-only behavior.

Priority usage

Spend selected accounts first, then leave the rest as fallback.

Priority accounts are visible on the same cards that show quota, disabled state, reset availability, recent errors, and model availability.

  • Use-first accounts show a visible Priority badge.
  • Disabled accounts stay visible but leave routing automatically.
  • Quota bars make exhausted and near-limit accounts obvious.
Scoped client keys

Limit prompts globally, by provider, or by individual account.

Managed API keys can expose only the providers and accounts a client should reach, with prompt ceilings applied before dispatch.

  • Whole-key prompt token limit protects every route behind that key.
  • Provider limits let Codex, Qwen, Claude, and Gemini use different ceilings.
  • Account limits protect a single upstream account from oversized requests.
Custom model routes

Publish stable ctm: aliases over changing provider pools.

A custom model is a route policy: ordered steps, weighted targets, exact account targeting, exclusions, and provider fallback in one dashboard card.

  • Expose a stable alias while changing providers behind it.
  • Combine Codex, Qwen, Claude, Gemini, and other targets in one route.
  • Use fallback steps when the first account is cooling down or out of quota.
Route testing

Send a real prompt through a route before handing it to clients.

Test API uses the dashboard session to exercise the same routing path clients use, then returns status, latency, selected model, output, and raw response.

  • Test direct provider models or ctm: aliases.
  • Validate prompt, instructions, and output ceiling from the UI.
  • Confirm successful routing before publishing client keys.
Request flow

Clients never talk to upstream accounts directly.

IO Gateway is the boundary. It receives client traffic, applies key limits and routing policy, then selects an eligible provider account.

  1. 01 Authenticate the client key Reject disabled keys and enforce prompt-token ceilings before dispatch.
  2. 02 Resolve the requested surface Normalize /v1, /codex, /claude, and ctm: aliases into route intent.
  3. 03 Select an eligible account Prefer priority accounts, skip disabled accounts automatically, then check quota, cooldown, and route scope.
  4. 04 Relay the stream Send the request upstream and keep usage, error, and notification state tied to the selected account.

Daily operation stays inside the dashboard.

Connect accounts, publish one gateway URL, then keep routing policy and client access inside the dashboard.

  1. 01 Add provider accounts Save subscription, consumer, and API-key credentials on your own server.
  2. 02 Choose priority accounts Mark one or more accounts as Use first; disabled accounts leave the priority path automatically.
  3. 03 Issue bounded client keys Set prompt-token ceilings for each key globally, by provider, or by account.
  4. 04 Watch quota and errors Use health, usage windows, cooldowns, reset timing, and alerts to act before failures.

Custom models are routing rules, not another model list.

A ctm: alias is a stable client name backed by ordered provider targets, account selection, load balancing, and fallback.

Stable aliases Expose names like ctm:research or ctm:coding instead of leaking provider-specific model IDs.
Ordered fallback Move to the next target when a provider is cooling down, out of quota, or unavailable.
Account targeting Point one alias at selected providers, selected accounts, priority pools, or mixed provider chains. 
model: ctm:research

Rust runtime

A Rust binary between clients and providers.

IO Gateway runs as a compiled Rust binary on Axum and Tokio, keeping routing, streaming, quota checks, and dashboard operations inside one low-overhead async service.

binary Single compiled server Deploy the gateway without a Node or Python runtime in the request path.
tokio Async streaming core Concurrent streams, retries, and upstream calls run through the async runtime.
rustls Rustls upstream HTTP Reqwest uses a Rustls TLS stack for outbound provider calls. 
cargo build --release
./target/release/io-gateway
